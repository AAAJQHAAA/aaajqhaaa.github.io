WebRTC 连接与信令

一、概述

WebRTC 会话生命周期：建立连接 → 传输数据 → 关闭连接。

WebRTC 连接需要信令服务器交换信息，实际连接由 ICE/STUN/TURN 完成。

浏览器 A ←─── 信令服务器（WebSocket 等）───→ 浏览器 B
              ↓ 交换 SDP offer/answer
浏览器 A ←─────────── ICE 连接 ─────────────→ 浏览器 B

关键点：信令服务器只是"传话筒"，实际数据传输不经过它。

二、信令（Signaling）

1. 为什么需要信令

WebRTC 无法自己发现对方，需要服务器帮忙传递信息。

问题：IP 地址不唯一

由于 NAT，多台设备共享一个公网 IP，设备没有唯一标识。

就像寄快递给朋友，只写名字"张三"，但没有地址

2. 信令方式选择

WebRTC 规范没有定义信令方式，开发者自己选择：

方式说明
WebSocket最常用
XMPP/SIP传统电话协议
HTTPS 轮询简单实现
邮件理论上可行
信鸽高延迟但可以

关键点：信令服务器只负责"传话"，不需要理解内容。

3. 信令交换的信息

类型内容
控制消息建立、关闭、错误处理
连接信息IP、端口（用于穿透 NAT）
能力协商支持哪些编解码器

交换的描述就是 SDP：

  • Offer：发起方描述自己的配置
  • Answer：接收方回应自己的配置

4. 信令消息类型

消息类型说明
video-offer呼叫方发起通话请求
video-answer被叫方回复接受
new-ice-candidateICE 候选信息
hang-up挂断

三、连接流程

连接时序图

下图展示了 WebRTC 完整的连接建立时序，包括 SDP 交换、ICE 候选协商、STUN/TURN 穿透等过程：

步骤详解

1. 双方各自创建 RTCPeerConnection
2. 设置 icecandidate 事件处理器
3. 设置 track 事件处理器
4. 商定信令服务器（WebSocket 等）
5. 连接服务器，加入同一会话
6. 交换 Offer/Answer 和候选地址
7. ICE 选择最佳路径建立连接
8. 媒体开始传输

细化流程：

1. A 点击用户名呼叫 B
         ↓
2. A 的浏览器创建 Offer（SDP）
         ↓
3. A 通过信令服务器发送 video-offer 给 B
         ↓
4. B 收到 Offer，创建 Answer（SDP）
         ↓
5. B 通过信令服务器发送 video-answer 给 A
         ↓
6. 双方开始交换 ICE 候选
         ↓
7. ICE 选择最佳路径建立连接
         ↓
8. 连接建立，音视频开始传输

四、核心代码

1. 创建连接

function createPeerConnection() {
  myPeerConnection = new RTCPeerConnection({
    iceServers: [{ urls: "stun:stun.stunprotocol.org" }]
  });

  myPeerConnection.onicecandidate = handleICECandidateEvent;
  myPeerConnection.ontrack = handleTrackEvent;
  myPeerConnection.onnegotiationneeded = handleNegotiationNeededEvent;
}

2. 发起呼叫

async function invite() {
  createPeerConnection();
  
  // 获取摄像头/麦克风
  const stream = await navigator.mediaDevices.getUserMedia({ audio: true, video: true });
  document.getElementById("local_video").srcObject = stream;
  
  // 添加轨道到连接
  stream.getTracks().forEach(track => myPeerConnection.addTrack(track, stream));
}

发起方创建 Offer 的核心步骤：

// 1. 获取本地媒体
const stream = await navigator.mediaDevices.getUserMedia({ audio: true, video: true });

// 2. 创建连接
const pc = new RTCPeerConnection();
stream.getTracks().forEach(track => pc.addTrack(track, stream));

// 3. 创建 Offer
const offer = await pc.createOffer();
await pc.setLocalDescription(offer);  // 设置本地描述

// 4. 发送 Offer 到 B（通过信令服务器）

3. 处理呼叫请求

async function handleVideoOfferMsg(msg) {
  createPeerConnection();
  
  // 设置对方的 Offer
  const desc = new RTCSessionDescription(msg.sdp);
  await myPeerConnection.setRemoteDescription(desc);
  
  // 获取本地媒体
  const stream = await navigator.mediaDevices.getUserMedia({ audio: true, video: true });
  
  // 添加轨道
  stream.getTracks().forEach(track => myPeerConnection.addTrack(track, stream));
  
  // 创建 Answer
  const answer = await myPeerConnection.createAnswer();
  await myPeerConnection.setLocalDescription(answer);
  
  // 发送 Answer 给呼叫方
  sendToServer({ type: "video-answer", sdp: myPeerConnection.localDescription });
}

接收方核心步骤：

// 1. 收到 Offer，设置远程描述
await pc.setRemoteDescription(offer);

// 2. 创建 Answer
const answer = await pc.createAnswer();
await pc.setLocalDescription(answer);

// 3. 发送 Answer 到 A（通过信令服务器）

4. 处理 ICE 候选

// 发送 ICE 候选给对方
function handleICECandidateEvent(event) {
  if (event.candidate) {
    sendToServer({
      type: "new-ice-candidate",
      candidate: event.candidate
    });
  }
}

// 收到 ICE 候选
function handleNewICECandidateMsg(msg) {
  const candidate = new RTCIceCandidate(msg.candidate);
  myPeerConnection.addIceCandidate(candidate);
}

5. 接收视频

function handleTrackEvent(event) {
  document.getElementById("received_video").srcObject = event.streams[0];
}

6. 挂断

function hangUpCall() {
  closeVideoCall();
  sendToServer({ type: "hang-up" });
}

function closeVideoCall() {
  // 停止所有轨道
  localVideo.srcObject.getTracks().forEach(track => track.stop());
  remoteVideo.srcObject.getTracks().forEach(track => track.stop());
  
  // 关闭连接
  myPeerConnection.close();
  myPeerConnection = null;
}

7. 信令服务器实现（简化）

WebSocket 服务器只需要支持：

// 1. 支持向指定用户发消息
function sendToUser(target, msg) {
  const conn = connections.find(c => c.username === target);
  conn.send(JSON.stringify(msg));
}

// 2. 转发未知消息类型
ws.on("message", (msg) => {
  const parsed = JSON.parse(msg);
  if (parsed.target) {
    sendToUser(parsed.target, parsed);  // 点对点
  } else {
    broadcast(parsed);  // 广播
  }
});

五、Pending 和 Current 描述

协商过程中，可能同时有多个 Offer 在考虑中：

类型说明
current已经双方同意，正在使用的配置
pending正在考虑中，还未最终同意的配置
场景：视频通话中，A 想从 480p 升级到 720p

A 发送新 Offer (720p)
        ↓
B 收到，但还没决定是否接受
        ↓
此时：
- current = 旧配置 (480p)  ← 仍在使用
- pending = 新 Offer (720p) ← 等待 B 同意

读取描述时：
  pending 有值 → 返回 pending（正在考虑中的）
  pending 为空 → 返回 current（正在使用的）

六、ICE 候选

除了交换 SDP，还要交换网络候选地址。

1. 候选类型（UDP）

类型说明
host直连 IP
srflxSTUN 发现的公网地址
prflx对称 NAT 产生的地址
relayTURN 中继地址

优先级：host > srflx > prflx > relay

2. 候选类型（TCP）

类型说明
active主动发起连接
passive等待接收连接
so同时发起

3. Trickle ICE

"冰块"式候选交换 —— 不等 Offer/Answer 完成，边协商边交换候选，加快连接速度。

七、ICE Restart（重启）

1. 什么时候需要

  • 用户切换网络（WiFi → 4G）
  • 网络拥塞
  • 连接失败

2. 原理

重新发起 ICE 协商，但保持旧连接直到新连接就绪。

pc.oniceconnectionstatechange = () => {
  if (pc.iceConnectionState === "failed") {
    // 1. 更新配置
    pc.setConfiguration(restartConfig);
    // 2. 触发重启
    pc.restartIce();
  }
};

3. 效果

旧连接（仍在工作）←→ 媒体流动
       ↓
   重启 ICE
       ↓
新连接建立
       ↓
媒体切换到新连接
旧连接关闭

八、ICE Rollback（回滚）

重新协商时如果失败，可以撤销当前 Offer，恢复到之前的稳定状态。

// 发送 rollback 类型描述
pc.setLocalDescription({ type: 'rollback' });

九、重要概念速查

概念说明
SDP会话描述协议，包含编码器、端口等信息
ICE交互式连接建立，负责找到最优传输路径
STUN帮助获取公网 IP
TURN中继服务器（无法直连时）

十二、总结

WebRTC 通话 = 信令服务器 + WebRTC 连接

1. 通过信令服务器交换 SDP（Offer/Answer）
2. 通过信令服务器交换 ICE 候选
3. WebRTC 自动建立直连
4. 音视频数据直连传输

信令服务器不参与实际通话，只是帮忙传递协商信息。
