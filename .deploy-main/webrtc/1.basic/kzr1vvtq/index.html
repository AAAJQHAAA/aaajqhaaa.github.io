完美协商

什么是完美协商

解决 WebRTC 协商中角色不对称的问题。

问题背景

传统协商需要区分"发起方"和"接收方"，代码不同，容易出错。

同时发 Offer

场景说明
视频通话应用A 和 B 同时打开页面，都想主动呼叫对方
重协商时网络抖动/切换 WiFi 后，双方都尝试重新协商
  • 碰撞
A 发 Offer 给 B
         ↓
A 还在等 Answer（signalingState 不是 stable）
         ↓
B 也发 Offer 给 A（双方同时想当 caller）
         ↓
A 收到 B 的 Offer，但自己还在处理中
         ↓
这就是碰撞！

完美协商的价值

不是为了处理"罕见错误"，而是为了：

  1. 简化代码 - 不需要区分 caller/callee，双方代码相同
  2. 应对重协商 - 通话中重新协商时也可能碰撞
  3. 防御性编程 - 网络波动时的极端情况

解决方案

双方都使用相同的代码，通过 polite/impolite 角色自动协调。

角色行为冲突时
Polite（礼貌）可以主动发 Offer，收到冲突时主动让步触发 ICE Rollback，放弃自己的 Offer
Impolite（不礼貌）收到冲突 Offer 直接忽略永远不放弃自己的 Offer
Polite 收到冲突 Offer：
  "好吧，我撤了，用你的"

Impolite 收到冲突 Offer：
  "不理你，继续用我的"

核心逻辑

发送 Offer 时

let makingOffer = false;

pc.onnegotiationneeded = async () => {
  makingOffer = true;
  await pc.setLocalDescription();  // 自动生成 offer 或 answer
  signaler.send({ description: pc.localDescription });
  makingOffer = false;
};

收到消息时

signaler.onmessage = async ({ data: { description, candidate } }) => {
  try {
    // ==================== 处理 SDP 描述 ====================
    if (description) {
      // ----- 步骤1：判断是否应该接受这个 Offer -----
      
      // 什么情况下可以接受 Offer？
      // 条件：我没有在发 Offer（!makingOffer）
      //   AND （状态是"稳定" || 正在处理对方的 Answer）
      const readyForOffer = !makingOffer && 
        (pc.signalingState === "stable" || isSettingRemoteAnswerPending);

      // 是否发生碰撞？双方同时发了 Offer
      const offerCollision = description.type === "offer" && !readyForOffer;

      // ----- 步骤2：根据角色决定是否忽略 -----
      
      // Impolite + 碰撞 → 忽略对方的 Offer
      // Polite + 碰撞 → 不忽略（会自动 Rollback）
      ignoreOffer = !polite && offerCollision;
      if (ignoreOffer) {
        return; // 忽略这个 Offer，后面的候选也不处理
      }

      // ----- 步骤3：设置远程描述 -----
      await pc.setRemoteDescription(description);

      // ----- 步骤4：如果收到 Offer，需要回复 Answer -----
      if (description.type === "offer") {
        // Polite 收到碰撞 Offer → setRemoteDescription 会自动 Rollback
        // 然后自动生成 Answer
        await pc.setLocalDescription();
        // 发送 Answer 给对方
        signaler.send({ description: pc.localDescription });
      }
    } 
    // ==================== 处理 ICE 候选 ====================
    else if (candidate) {
      try {
        await pc.addIceCandidate(candidate);
      } catch (err) {
        // 如果我们忽略了这个 Offer，它的候选也忽略
        if (ignoreOffer) return;
        throw err;
      }
    }
  } catch (err) {
    console.error(err);
  }
};

角色分配

只要双方一方是 polite，另一方是 impolite 即可：

// 方式1：先连的是 polite
const polite = isFirstConnected;

// 方式2：随机数大的赢
const polite = myRandom > peerRandom;

流程图

情况1：正常协商
  A (polite) 发 Offer
        ↓
  B 收到 → 发 Answer
        ↓
  协商完成

情况2：碰撞（同时发 Offer）
  A (polite) 发 Offer
  B (impolite) 也发 Offer
        ↓
  B 收到 A 的 Offer → 忽略（impolite）
  A 收到 B 的 Offer → 自动 Rollback（polite）
        ↓
  A 改发 Answer
        ↓
  协商完成

关键点

  1. 双方代码相同 - 不需要区分 caller/callee
  2. Polite 会 Rollback - 收到冲突时自动让步
  3. 用 makingOffer 标志 - 防止竞态条件
  4. 忽略 Offer = 忽略其 Candidate - 避免错误
